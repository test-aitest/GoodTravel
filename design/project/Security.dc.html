セキュリティとモデル

ワーカーは顧客のPCに入り、その顧客のログインで操作する。だから「AI に何を見せ、何を決めさせるか」を最初に絞る。11/13 決定。

誰が決めるか：4段のはしご

ふだんは段 0 で台本をまとめて実行する。確認に通らなかった手順だけを段 1 以降に上げ、決まったらその続きから台本に戻る。上げ下げを決めるのは AgentField の reasoner run_job。段 0・1 は AI を使わない skill、段 2・3 は reasoner の中で動く。どの段で決まったかと費用は、全部同じ流れ図に残る。

段 0PandaScript（AI なし）ふだんの再実行。保存した台本を Lightpanda の中でそのまま実行する速い道。要素が1つだけあるかと、操作後の状態も台本の中で確かめる操作：PandaScript（顧客のPCの Lightpanda で lightpanda run）
呼び出しと記録：AgentField の skill replay_script上がる条件：確認に通らない
段 1要素ツリー（AI なし）役割・名前・どのフォームの中かで探し直す。1つに決まれば実行し、台本を作り直す操作：Lightpanda の要素ツリー
呼び出しと記録：AgentField の skill refind_by_tree上がる条件：一致が0件か2件以上
段 2Claude Opus 5.5 · effort medium初回の手順づくりと修復だけ。決まった形の JSON で「どの要素か」を返させる判断：Claude
呼び出しと記録：AgentField の reasoner run_job の app.ai()上がる条件：「確信なし」と返したとき
段 3あなた承認待ち。AgentField 本体に保存されるので、再起動しても消えない判断：あなた
待ちと記録：AgentField の reasoner run_job の app.pause()書き込みの前は、どの段で決まっても必ずここを通る
PandaScript（手）と AgentField（監督）を分ける理由 1. 置き場所：ページとログインに触る処理は顧客のPCの中、どの段に上げるか・承認・どの顧客のPCを使うかの判断はPCの外。ページに仕込まれた指示が判断の側に届かず、ログイン情報もPCの外に出ない 2. 待つ時間：台本は数秒で終わるが、承認は何時間も待つことがある。再起動しても消えない待ちは AgentField が持つ 3. 速さ：1回押すたびに外から指示すると遅い。台本はPCの中で一気に流し、AgentField は確認に通らなかった手順のときだけ出てくる。台本の中からは要素ツリーも Claude も呼べないので、失敗したあとの判断は外が受け持つ
  • モデルは1つだけ。effort は medium（Opus 5.5 の既定）で運用を始める（11/14 決定）。1手ごとの仕事は「絞った一覧から1つ選ぶ」だけで、安全は要素の検査・書き込み前の承認・全行の読み直しが担うため。xhigh は1手ごとに時間がかかりすぎるので使わない
  • high に上げる合図：初回の手順づくりで「承認画面で人が直した」「読み直しで一致しなかった」「Claude が確信なしで人に回した」のどれかが出たとき。effort は呼び出しごとの設定なので、その顧客やサイトだけ上げられる。数えるのは AgentField の流れ図で。medium と high を比べる検証は、開発が終わってから行う（ハッカソン中はしない）
  • fast mode は料金が2倍になるので使わない。初回の手順づくりは1度きりで裏で動くので、進み具合を画面に出して待つ。速さは「送る量を減らす」で稼ぐ
  • 初回の手順は「承認 → 書き込み → 全行の読み直しで一致」まで通ったときだけ保存する
  • PandaScript と要素ツリーは二者択一にしない（11/14 決定）。台本は AI に書かせず、確かめ終わった手順から組み立てる。CSS セレクタで動く台本と、役割と名前で探す要素ツリーは得意な場面が違うため、両方の手がかりを保存する
  • AgentField のエージェントは Python で書く（再起動に強い app.pause() は Python の SDK だけにあるため）。画面からは REST で呼ぶ

守ること

起こりうること対策
ページに仕込まれた指示に AI が従うAI が返せるのは「今の要素ツリーにあるボタンや欄を1つ選ぶ」形の JSON だけ。URL・送信先・入力する値は AI に決めさせない。選ばれた要素は実行器が役割・名前・どのフォームの中かで検査し、外れたら止める
ログイン情報が AI や記録に漏れるAI には一度も見せない。保存する手順には「vault の Maruyama パスワード」という参照だけを書く。本物の値は実行の直前に、その顧客のPCの中で埋める（PandaScript の $LP_* 置き換え）
顧客の中身が AI 事業者に渡る送るのは要素の役割と名前だけ。表の数値や顧客名は伏せてから送る。2回目以降は何も送らない（段 0・1 で終わる）
別の顧客のPC・ログイン・メモリに届くどれを使うかは依頼の顧客IDからサーバー側で決め、AI の返答では決めさせない。判定はコードの1か所だけ。AgentField のメモリも顧客ごとに分ける
PCから外へ勝手に通信するDaytona の通信許可リストで、その顧客のサイトだけに絞る
AI が間違えたまま書き込む書き込み前は人の承認、書き込み後は全行の読み直し。どの段で決まっても外さない
記録や設定から漏れるAgentField のテレメトリを止める。ネットに出すときは API キーを必須にし、承認の受け口には署名の鍵を設定する。記録に残す文も中身を伏せる

AI 事業者とデータの扱い

  • 使うのは Anthropic の Claude Opus 5.5 だけ。LiteLLM の設定で使ってよいモデル名を固定し、ほかの事業者へは流れないようにする
  • Anthropic の API は、既定では送った内容を学習に使わない。より厳しい顧客には、保存しない契約（ZDR）や推論する地域の指定も選べる。最上位の Fable 5.2 は ZDR で使えないと明記されているため使わない
  • 顧客ごとに「AI を使ってよいか」を設定できる。使わない顧客は段 2 を飛ばし、PandaScript と要素ツリーで決まらなければすぐ人に回す

運用コスト（目安）

お金がかかるのは初回と修復だけ。2回目からは AI に1円も払わない。数字は high を想定した多めの見積もりで、medium ではこれ以下になる見込み。運用の実測で差し替える。

  • 保存した手順だけで動く定時実行でも、書き込みの前に毎回承認を求めるか。今は求める（画面 4・5 もそうしている）。顧客のルールで「N件以下なら自動で保存」にする案もある
